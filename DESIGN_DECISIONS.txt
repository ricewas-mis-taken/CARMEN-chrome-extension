CARMEN FOCUS — DESIGN DECISIONS LOG
=====================================
An append-only record of real architectural/design choices for this app --
not bug fixes, not routine implementation detail. A "design decision" here
means: there were at least two genuinely different ways to do something,
one was picked deliberately, and future-you (or future-me) would otherwise
have to re-derive the reasoning from scratch or accidentally re-litigate it.

Add a new dated entry every time a decision like that gets made -- see
FEATURE_IMPLEMENT.txt's own checklist, which has a step reminding to update
this file for exactly that reason. Newest entries go at the bottom.

Canonical copy lives in carmen-desktop's DESIGN_DECISIONS.txt; keep this
copy in sync with it -- most entries affect both repos anyway.

Format per entry:
  [YYYY-MM-DD] Short title
  Decision: what was chosen.
  Why: the reasoning / what alternative was rejected and why.
  Scope: what this does and doesn't apply to, if not obvious.

-------------------------------------------------------------------------

[2026-09-25] Edit Task vs Edit Session Rules are two deliberately different tools
Decision: Editing a Task's rules (qt_ui/task_editor.py) always updates the
task's own stored template AND, if that exact task's own session is the one
currently running (session_manager.get_status()'s source/eventId matches),
applies the change live too. "Edit Session Rules" (qt_ui/picker_dialogs.py)
only ever touches the live session, never persists to any template.
Why: these solve different problems -- "I want this task's rules different
from now on" vs "just for this one session, do something different" -- and
collapsing them into one tool would force a false choice every time either
is used.
Scope: the live-apply check matches on source in ("task", "review") --
a review timer linked to this task also carries its eventId (see the entry
below), so editing/deleting the task must recognize that case too, not
just plain source == "task".

[2026-09-25] Deleting a task ends its own currently-running session
Decision: qt_ui/task_editor.py's delete flow checks the same source/eventId
match as the live-edit path above, and calls session_manager.end_session()
first if this exact task is what's running.
Why: leaving an enforcement session running against a task that no longer
exists is a worse default than ending it -- there's nothing left to point
the session's UI/history at.
Scope: only the exact task whose own session is running gets ended;
editing/deleting an unrelated task never touches a different task's live
session.

[2026-09-25] The local API server must run threaded
Decision: api_server.py's app.run() uses threaded=True.
Why: confirmed live -- without it, Werkzeug's single-worker dev server lets
one wedged/slow request permanently block every other request forever,
including trivial ones with no I/O of their own (GET /health). This isn't
a performance tweak, it's a correctness requirement: this API has multiple
concurrent pollers (the extension's background.js, the Qt UI, the popup)
that must never be able to starve each other.

[2026-09-25] apiFetch (extension) must always resolve in bounded time
Decision: chrome/background.js and firefox/background.js's apiFetch()
wraps its fetch() call in a 5-second AbortController timeout.
Why: fetch() has no default timeout. Paired with the desktop-threading
decision above, a wedged desktop app used to hang every single extension
call forever instead of ever reaching the existing "desktop unreachable"
fallback -- the fallback code was already correct, it just never got a
chance to run.

[2026-09-25] A review timer is independent of session_manager's one active session
Decision: review_store.py's review-in-progress tracking (_active_sessions)
stays completely separate from session_manager._state. Starting a review
while a different session (e.g. a pomodoro/task session) is already active
does NOT create a second session_manager session and does NOT touch the
existing one in any way -- it just times independently in the desktop UI's
own review banner. Ending either one never affects the other.
Why: session_manager is a single-session model by design (one endTime, one
lockMode, one blocklist at a time) -- making it support two truly
overlapping sessions with independent enforcement rules would be a much
larger, riskier rearchitecture for a need that's actually already served
by keeping review timing as its own separate concept.
Rejected alternative: a stack/queue of concurrent session_manager sessions
with priority-based enforcement. Not implemented -- the enforcement rules
in effect are still whichever single session_manager session is actually
active, if any; a review never overrides or suspends it.

[2026-09-25] "Review has priority" means display priority, not enforcement priority
Decision: GET /status gains a reviewInProgress field, populated from
review_store.get_active_review() independent of whatever session_manager
reports as the active session (deduped only when it's literally the same
review driving that session, to avoid showing it twice). The extension
renders this as an always-visible banner above whichever main view (setup
or active-session) the popup is otherwise showing, and keeps polling alive
for it even when no other session is active.
Why: this was the direct, minimal fix for a real bug -- a review started
alongside an unrelated session (e.g. a pomodoro) was completely invisible
to the extension, and cancelling that unrelated session made the popup
show nothing at all even though the review was still legitimately running
in the desktop app. "Review should have priority over the pomodoro" was
interpreted as "the review must always be visible, prominently, regardless
of what else is or isn't happening" -- not as "the review's rules should
override the other session's lock mode/blocklist," which the previous
entry's decision explicitly keeps separate.
Scope: this only affects display. It does not change which
lockMode/processBlocklist/domainWhitelist is actually enforced at any
given moment -- that's still governed entirely by whichever single
session session_manager reports active, per the entry above.

[2026-09-25] An independent review's pause state lives in review_store, not the Qt widget
Decision: review_store.py's _active_sessions entries now carry their own
pause bookkeeping (accumulated_seconds/resumed_at/auto_paused), with
pause_active_review()/resume_active_review()/auto_pause_for_break()/
auto_resume_from_break() as the only ways to change it. qt_ui/review_tab.py's
_ReviewBanner delegates to these for any review with a real review_store
token (_is_independent_review()) instead of using its own local
_is_paused/_accumulated_seconds fields, which it still uses unchanged for
the one case that has no review_store token at all (the first-attempt flow,
timing a problem that doesn't exist in the DB yet).
Why: a pomodoro's break phase needed to auto-pause a review running
alongside it (see session_manager._advance_pomodoro_locked), and the
extension needed to both see that pause state and let the user manually
undo it. Neither is reachable if pause state only lives on a QWidget
instance that may not even be constructed at the time (the desktop UI
doesn't have to be on the Review tab, or open at all) -- it has to live
in the same place get_active_review() already reads from.
Scope: this does NOT apply to a review driving session_manager's own
session (end_session_on_finish=True) -- that one already deferred to
session_manager.pause_session()/get_status()["isPaused"] as its source of
truth, unchanged.

[2026-09-26] Popup's "multiple things running at once" UI is a generic expandable chip, not bespoke boxes
Decision: the pomodoro info box and the review-in-progress banner both
became instances of one shared pattern (.info-chip in popup.css): a
collapsed row (short label, a big prominent time value, a chevron) that
toggles an .info-chip-detail panel on click. The review chip additionally
colors itself via a --review-color CSS custom property set from the
problem's own subjectColor (color-mix() derives the tinted
background/border from it), and shows a "Paused (on pomodoro break)" /
"Paused" line plus a Pause/Resume button (POST /review/pause,
POST /review/resume) in its detail panel.
Why: asked for directly -- multiple simultaneous timers should read as
small boxes with a bigger time next to the label, not a label with a tiny
time underneath, and clicking one should reveal its own detail rather than
cluttering the collapsed view. Building it as one reusable pattern instead
of two different bespoke layouts means a third concurrent "thing" later
only needs new content, not new interaction/CSS work.
Scope: the main countdown at the top of the popup (session.endTime,
already the pomodoro's own current-phase deadline during a pomodoro) is
left as the single big primary display -- the pomodoro chip mirrors that
same value (see startCountdown's tick()) rather than computing a second,
subtly-different one, and only adds the cycle count on expand. The CARMEN
logo/header was also hoisted out of both setup-view/active-view sections
into one shared header above everything (including the review chip),
since it was previously duplicated per-view and the review chip needed to
sit visibly below it regardless of which view is showing.

[2026-09-26] A hard-locked tab's title/favicon are cloaked, not just its focus
Decision: any tab sitting on a non-whitelisted domain while a hard-lock
session is active and not paused/on break gets content/cloak.js injected,
which overwrites its title to a plain "CARMEN HIDDEN" and its favicon to a
generic lock icon, re-asserting both on a 500ms interval. background.js's
sweepTabsForCloak() checks every tab (not just the one just redirected
away from) on a periodic tick and on every qualifying tab-URL event, so a
tab that lands on a bad domain in the background (window.open,
target=_blank) without ever being focused gets caught too -- the
extension-side equivalent of carmen-desktop's own
sweep_minimize_blocked_windows(). Cloaks are tracked in a cloakedTabIds
set. Two things clear a cloak: uncloakAllTabs() (session ended, got
paused, or entered a break -- checked in sweepTabsForCloak()'s own
early-return) and uncloakTab() for one specific tab, the moment ITS domain
becomes whitelisted -- called both instantly from handleTabUrl's own
whitelisted branch (that tab navigating there itself) and, as a safety
net, from sweepTabsForCloak() (covers the whitelist changing mid-session
for a tab that never re-navigated).
Why: hard lock never touches the offending tab's own URL, on purpose (see
the existing comment on switchAway's else-branch) -- but that means the
real page's title and favicon kept showing in the tab strip the whole time
it sat there, silently advertising exactly what was being looked at even
though the tab itself was no longer usable.
Rejected alternative #1: cloaking only the specific tab switchAway() just
redirected away from. Not used -- a tab opened directly to a bad domain in
the background, never focused, would never get caught at all under that
narrower trigger.
Rejected alternative #2: a violation count in the cloaked title (e.g.
"CARMEN HIDDEN (#3)"). Dropped -- just "CARMEN HIDDEN", nothing else.
Rejected alternative #3: a MutationObserver on the <title> node to catch
the page trying to change it back. Not used -- a page can also replace the
node entirely, rewrite <head> wholesale (common on SPA route changes), or
never touch the DOM node at all (direct `document.title = ...`), so a
simple periodic re-assertion is both less code and more reliably correct
than trying to intercept every path that could revert it.
Scope: soft lock is intentionally left alone -- it's meant to let the user
stay on the page after a warning, so cloaking a tab they're allowed to
keep using would be actively wrong, not just unnecessary.

[2026-09-28] sweepTabsForCloak() re-cloaks unconditionally; cloakedTabIds is
no longer a gate against re-cloaking
Decision: cloakedTabIds is background.js's only record of "is this tab
cloaked" -- the real cloak state lives inside content/cloak.js's own
in-page closure, which is destroyed the instant that tab navigates,
reloads, or gets redirected. sweepTabsForCloak() used to skip a tab
entirely once cloakedTabIds already had it (`if (!cloakedTabIds.has(tab.id))
{ cloakOffendingTab(tab.id); }`), on the assumption that a cloaked tab
stays cloaked until something explicitly uncloaks it. That assumption
breaks the moment a cloaked tab silently redirects to a DIFFERENT
non-whitelisted page (meta-refresh, an SPA route change, an ad redirect
chain): the new page has no cloak.js running yet and briefly shows its
real title/favicon, but the sweep sees the stale cloakedTabIds entry from
before the redirect and never re-applies the cloak.
Now the per-tab loop cloaks every non-active, non-whitelisted http(s) tab
unconditionally on every sweep, dropping the cloakedTabIds gate entirely
from that loop. This relies on content/cloak.js's cloak() already being
idempotent -- re-invoking it on an already-cloaked tab reasserts the same
"CARMEN HIDDEN" title/lock favicon (a no-op in effect) and, critically,
never re-captures "CARMEN HIDDEN" itself as the "original" title/favicon
to restore on uncloak, since cloak() only saves originalTitle/
originalFavicons the first time (`if (!cloaked) { originalTitle = ... }`).
cloakedTabIds itself is kept for the bookkeeping that still needs it:
uncloakTab()'s no-op guard, uncloakAllTabs() knowing which tabs to
message, and the sweep's own uncloak-on-whitelist check just above this
loop -- it's just no longer read as "don't bother cloaking this one
again."
Note: this supersedes part of the [2026-09-26] entry above, which
described cloakedTabIds as preventing "re-inject[ing] + re-messag[ing] a
tab that's already cloaked every single sweep" -- that's exactly the
behavior this fix removes.
Why: a periodic sweep whose entire job is catching cloak state drifting
out of sync (see that same entry) must itself be safe to run redundantly
against tabs it already believes are handled -- otherwise it can't
self-heal from exactly the kind of desync (a stale Set entry after a
same-tab redirect) it exists to catch.

[2026-09-28] chrome.alarms/browser.alarms never unilaterally ends a session --
it only ever prompts a status recheck
Decision: the ALARM_NAME alarm armed at session start (and re-armed on
pause/resume) used to fire and unconditionally POST /session/end + finalize
the UI the moment its endTime passed. That's wrong whenever the desktop's
own state has moved on without this extension's alarm hearing about it --
a pomodoro rolling to its next phase/break (advanced server-side inside
carmen-desktop's _get_status_locked, with a brand new endTime), or a
pause/resume that happened from the desktop side rather than through this
extension's own pauseSession/resumeSession handlers. In both cases the
armed alarm is just stale, not evidence the session ended.
Now, the alarm firing (and, separately, this file's own regular
getSession()-polling path in sweepTabsForCloak, which already runs every
POLL_INTERVAL_MS regardless of lock mode) both feed into one
reconcileAlarmWithSession() helper: it re-arms the alarm against whatever
endTime the desktop is currently reporting, clears it while paused/inactive,
and otherwise leaves it alone. onAlarm's own handler for ALARM_NAME calls
getSession() first -- which is also literally the GET /status call that
self-finalizes a truly-expired session or advances a pomodoro phase on the
desktop side -- and only proceeds to POST /session/end + show the
completion notification if that fresh status confirms the session is
genuinely no longer active. A session still reported active after that
check (new phase, or resumed) just gets its alarm re-armed and nothing else
happens -- no POST, no notification.
A browser-only (no desktop) session is explicitly exempted from all of
this: its alarm is entirely self-managed by this file's own
startSession/pauseSession/resumeSession/endSession handlers, with no
external actor able to move its endTime out from under it.
Why: same bug class as the corresponding fix already made in
carmen-desktop (two places tracking the same "is this session still
running" state, able to independently drift) -- here the alarm was a
second, unsynced tracker of session-end alongside the desktop's own
authoritative state.
Rejected alternative: have the alarm handler blindly re-fetch and re-arm
without ever ending anything itself, deferring all end-of-session
detection entirely to the popup's polling. Not used -- the popup isn't
guaranteed to be open, and this file already has its own
always-running sweepTabsForCloak() polling loop capable of driving this
independently of whether the popup is open.
Left as-is: if the desktop is unreachable when the alarm fires,
getSession() falls back to its existing defaultSession() (isActive: false)
behavior, so this ends up taking the same "assume ended, try to POST
/session/end anyway, let it fail silently" path this code already took
on any desktop-unreachable error before this fix -- not a new failure
mode, just preserved.

[2026-09-29] reconcileAlarmWithSession's re-arm comparison must tolerate
sub-second Date.now() drift, and must never arm an alarm already in the past
Decision: this supersedes part of the [2026-09-28] entry above -- that entry
covers why the alarm is never allowed to unilaterally end a session, and
that part still stands unchanged. This entry covers a second, independent
bug in the same function that entry introduced: reconcileAlarmWithSession()
compared session.endTime against lastArmedAlarmEndTime with !==, but
getSession() recomputes endTime fresh on every single call as
Date.now() + secondsRemaining*1000. Even when the desktop reports the exact
same secondsRemaining tick after tick, the raw endTime still drifts by a few
ms every call purely from Date.now() advancing -- so the !== check was true
on essentially every reconciliation, and a desktop that kept reporting a
deeply negative (or otherwise stuck-in-the-past) secondsRemaining caused the
alarm to be re-armed forever, always against a `when` already in the past.
Now: (1) the comparison rounds both sides to the nearest second
(Math.round(endTime / 1000)) before comparing, so ordinary ms-level drift no
longer looks like a change worth re-arming for; (2) separately, if
session.endTime is already <= Date.now() -- genuinely in the past, not just
"hasn't fired yet" -- the alarm is cleared instead of armed. Arming a
already-past `when` fires immediately (chrome.alarms/browser.alarms have no
minimum-future-time enforcement), which just re-enters the same stale-endTime
state on the very next tick.
Why clearing (not ending the session) is safe: sweepTabsForCloak's own
regular getSession()-polling loop (every POLL_INTERVAL_MS, unconditional of
lock mode -- see that function's own comments) re-derives session.isActive
fresh on every tick regardless of whether an alarm is armed, so clearing the
alarm doesn't stop this from being re-checked; it only stops a doomed alarm
from repeatedly firing in the meantime. Ending the session is still left
entirely to getSession() confirming isActive: false, exactly as the
[2026-09-28] entry requires -- this fix does not touch that path and does
not let the alarm (or its absence) decide anything about session state on
its own.
Rejected alternative: skip re-arming whenever session.endTime <= Date.now()
without clearing the existing alarm. Not used -- a previously-armed alarm
from before the desktop started reporting a stuck-in-the-past endTime would
otherwise sit there, already fired or about to, contributing nothing further
and just leaving lastArmedAlarmEndTime pointing at a stale value that could
mask a later, legitimate re-arm if the desktop's endTime happened to round
to the same second again.

[2026-10-03] Cloak sweep reloads discarded tabs; cloaked tabs get a blank cover
Decision: sweepTabsForCloak() reloads a qualifying tab whose tab.discarded
is true instead of trying to inject content/cloak.js into it, and cloak.js
now covers the page with an opaque full-viewport div (on <html>) and uses
the extension's own icon128.png (inlined as a data URI) as the favicon
instead of the old lock glyph.
Why: tabs inside a collapsed tab group are typically discarded, so
chrome.scripting.executeScript failed silently and they kept their real
title/favicon until clicked. The cover blanks the page screenshot that
hover cards / vertical-tab previews show; the browser's own hover card
still shows the domain, which an extension cannot hide.
Rejected alternative: leaving discarded tabs alone until activated. Not
used -- that is exactly the leak this fixes. Cost accepted: a discarded
blocked-domain tab is loaded in the background once so it can be cloaked.

[2026-10-03] Cloak sweep is event-driven, parallel, and per-tab timed out
Decision: sweepTabsForCloak() now runs on tab created/updated/activated,
window focus and tab-group events (not only the 7s tick), coalesces
overlapping runs, handles every qualifying tab in parallel with a 4s
per-tab timeout, and tries a cheap sendMessage before re-injecting
content/cloak.js. cloak.js also reasserts the title via a MutationObserver
(200ms interval kept as backstop).
Why: cloaking waited up to POLL_INTERVAL_MS for the next tick, and the old
serial loop meant one tab whose executeScript never settled (frozen tabs,
common in collapsed tab groups) blocked every tab after it -- so grouped
tabs stayed uncloaked until clicked.
Rejected alternative: just lowering POLL_INTERVAL_MS. Not used -- it polls
the desktop faster for everything and still leaves the serial-stall bug.

[2026-10-03] Uncloaking no longer depends on in-memory state
Decision: cloakedTabIds is persisted to storage.local and re-hydrated on
worker start; uncloakAllTabs() messages every open web tab (not just the
tracked ids) once anything was cloaked; cloak.js's favicon restore removes
any leftover cloak-icon link (page replaced its <head> links) and, for a
page that had no <link rel=icon>, re-declares /favicon.ico.
Why: favicons stayed on the cloak icon after a session ended -- the MV3
worker restarting emptied the in-memory set so nothing got an uncloak
message, and a page with no icon link never made the browser re-request its
default favicon after our injected link was removed.

[2026-10-04] Review chip hangs under the pomodoro chip, colored by its task
Decision: while a session is active, the review-in-progress chip (from
/status reviewInProgress) is rendered directly under the pomodoro chip as a
compact, same-style expandable chip labeled "Review: <problem>" with time
elapsed; with no session active it stays at the top of the popup. Its color
is the linked task's color (reviewInProgress.taskColor), falling back to the
problem's subject color when the topic has no linked task.
Why: with a pomodoro running, the review read as a separate full-size banner
far from the timer it runs alongside; a small task under the pomodoro shows
the relationship.
Rejected alternative: coloring by subject color only (the previous
behavior) -- the user wanted the chip to read as belonging to the task.
Cross-reference: carmen-desktop DESIGN_DECISIONS.txt [2026-10-04] (status
reviewInProgress gains taskColor).

[2026-10-06] War-room fixes: one verified patch per bug, plus a regression check per bug
Decision: a second ten-agent round (see the referee report) found 59 distinct
bugs, 43 in chrome/ and firefox/ and 16 in the older carmen-extension-sharing
copy. One verified patch per bug was applied; 51 applied as written and 8
collided in isWhitelisted, the save-sites notification code, getBaseDomain,

categorizer, and were merged by hand. Each fix ships with its check script in
tests/regression/, runnable as `node tests/regression/run-all.mjs` from the

in FEATURE_IMPLEMENT.txt no longer holds for these. Interaction fixes: a
whitelisted-entry normalisation chain (wildcard, query/fragment, port,
IDN/trailing dot) now lives in one place; the save-sites click falls back to
the single pending prompt when no per-task entry exists (older stored
prompts); two test harnesses were taught about shadow DOM and array-key
storage reads.
Why: every distinct bug had a reproduced script and a before/after check, so
keeping those as a regression suite is cheap and stops these coming back.
Cross-reference: carmen-desktop DESIGN_DECISIONS.txt [2026-10-05] (the
desktop's fixes from the first round, same approach).

[2026-10-09] The extension keeps a long request open to the desktop to react instantly
Decision: background.js runs wakeLoop(): one request at a time to the
desktop's GET /events/wait?since=<version>&timeout=20. A "changed" answer runs
sweepTabsForCloak() right away (which re-checks the active tab when enforcement
starts). The 7s poll stays as the backstop; failures back off 2/5/15/30s and
never throw. Restarted by the 1-minute alarm if the worker was put to sleep.
Why: a session started on the desktop while the user sat on a distracting tab
waited up to 7s to be noticed. Wake-up is only a hint, so correctness never
depends on it.
Cross-reference: carmen-desktop DESIGN_DECISIONS.txt [2026-10-09] (the
/events/wait endpoint and change counter).

[2026-10-10] Popup lists the desktop's waiting (paused) sessions, with Switch and End
Decision: GET /status now carries parkedSessions (paused sessions set aside
while a different one runs, next-to-return first, any number). background.js
passes the list through on every path (empty for an older desktop or browser-only
mode) and the popup shows a "Waiting (paused)" box with one row per session:
name, then time left (timed) / worked time (reviews, burnout) / pomodoro cycle.
Each row has Switch (POST /session/parked/switch: that session runs, the current
one takes its place paused, session-end alarm re-armed) and End (POST
/session/parked/end; needs a second click because it files the session into
history for good). Both send the row's parkId, never "the next one", since any of
many can be picked; the desktop answers 404 for an id that is no longer waiting.
Why: a task paused while another runs used to vanish from the extension entirely.
Switch/End were first left out (display only) and added on request.
Cross-reference: carmen-desktop DESIGN_DECISIONS.txt [2026-10-10] (waiting sessions).
